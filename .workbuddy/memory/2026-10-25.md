## 新增流体提取机与原料精炼机（commit `900afac`）

### 流体提取机（`fluid_extractor`）

- 配方类型 `FluidExtractingRecipe`（**不继承 `InspiredRecipe`**：那个基类产物是 `ItemStack`，
  这里产物是流体），三件套 + `ModRecipes` 注册，JSON 落在 `recipe/fluid_extracting/`。
- 方块实体：单输入槽 + 16,000 mB 输出罐（`Action.DRAIN`，组件名 `fluid_output`）。
  合成走统一 `machine(...)` 形状：翡翠钢 + 下界合金锭 + 强能核心。
- 比例「一锭 = 144 mB」，粒 16、块 1296。目前只有等离子一种流体（PLASMA 没有块/粒形态，
  所以只出了一条配方）。

### 原料精炼机（`raw_refiner`）

- 配方类型 `RefiningRecipe`（**继承 `InspiredRecipe`**，主产物走基类 `result`），
  副产物写成 `List<ItemStack>` 而不是两个字段 —— 空列表表示没有副产物，
  且 6 个字段正好卡在 `StreamCodec.composite` 的上限（写成两个字段就是 7 个，得手写 `of`）。
- 三个输出槽是**同一个库存组件的三个格子，竖排在 x=116**（横向摆会撞到 x=150 的充能罐）。
- 合成 **不走统一形状**：统一形状固定 5/3/1，这里要 3 钙锭 / 5 无恒合金 / 1 高能核心，
  自己写 `SCS / CHC / SSS`。用钙锭是因为**幽匿合金已被结构模拟机占用**。
- 8 条配方：原版三粗矿、粗钫盐/粗铯盐 → 盐、两种盐 → 锭、核废料 → 铀锭 + 镎尘 + 钚尘。

### 回收升级

- 新插件类型 `BYPRODUCT`，**唯一加算**的插件（`byproduct += multiplier - 1`，两个是 ×3 不是 ×4），
  也是唯一只有特定机器读它的插件（只有 `RawRefinerTile` 调 `byproductCount`）。
- 装配配方：思维矩阵锭 + 144 mB 液态等离子 —— 第一份「产物流回装配台」的配方。

## 本轮新坑

1. **罐体设 `Action.DRAIN` 后自身灌入必须 `fillForced`**。普通 `fill` 被动作校验挡掉并静默返回 0，
   表现为「原料被吃掉、罐里一滴都没有」。与 `Action.FILL` 的罐要 `drainForced` 是同一个坑。
2. **`getHandlerFromName` / `serverTick` 在 `ActiveTile` 上，不在 `BasicTile`**。
   自检代码的泛型边界要写 `T extends ActiveTile<T>`，写 `BasicTile<T>` 编译不过。
3. **多输出槽必须先确认所有格子都塞得下再扣材料**，真正写入时留快照、任一格失败整批回滚，
   否则副产物槽满了会吞原料或白送主产物。

### 推送（github.com:443 又 502，走了 REST 兜底）

`api.github.com` 通、`github.com` 不通 → 用脚本把 `origin/master..HEAD` 逐个重放（blob/tree/commit/ref），
三个提交 sha 与本地逐个对齐。脚本在 `%TEMP%/gh_rest_push2.py`。这次踩到两个新的：

1. **`git diff-tree A B` 的 A 是「旧」、B 是「新」**，写反了会把「新增」读成「删除」，
   API 报 422 `GitRPC::BadObjectState`（删一个 base_tree 里本来没有的路径）。
   保险写法是单参数 `git diff-tree --name-status -r <sha>`。
2. **树的 entries 不支持 `encoding: base64`**（只有 `/git/blobs` 支持）。二进制（PNG）
   必须先 `POST /git/blobs` 拿 sha 再在 tree 里引用，否则内联的 base64 会被当文本写坏，
   提交 sha 对不上（表现是「其他文件都对，只有 PNG 变了」）。
3. 另外 `git ls-tree` 默认会给中文路径加引号（`core.quotepath`），比对前加 `-c core.quotepath=false`。

## 创造栏改成自动、核废料主产物改铀粒

### 创造栏不再需要手动加

用户问「不能扔进注册物品的函数里吗」，答案是**大部分能**，做法分两层：

1. **机器** —— 灵感页改成遍历 `MachineRegistry.machines()`。机器本来就要走
   `MachineRegistry.register(...)`（语言/状态/标签/战利品都靠它），顺手把创造栏也接上，
   注册顺序同时成为创造栏顺序（所以 `ModMachines` 里的先后现在有双重含义）。
2. **其余物品** —— 灵感页末尾加一层**兜底循环**：把 `CreativeModeTab.Output` 包一层记下
   `placed`，收尾时遍历 `BuiltInRegistries.ITEM`，凡是本模组注册、又没被两页收走的物品一律追加。
   兜底要排除材料页那批（`materialItems()` 从 `ModMaterials` 现算），否则同一件东西会出现在两页。

`CreativeModeTab.Output` **不是函数式接口**（唯一的抽象方法是
`accept(ItemStack, TabVisibility)`，其余 `accept` 重载都是 default），所以包装要写匿名类、
实现 `accept(ItemStack, TabVisibility)` —— 写 lambda 会报「不兼容的类型」。

自检：灵感页 103 项、材料页 39 项（与改之前一致，说明既没漏也没重复）；「没进任何一页的物品：无」；
灵感页最后三项仍是 `Reaction Core / Nuclear Waste / Basalt Base` → 兜底循环这次没补任何东西，
证明显式清单本身是完整的。另外核对了「材料页里不属于锭类材料的条目：无」「重复条目：无」。

### 核废料主产物：铀锭 → 铀粒

`RefiningRecipes` 里核废料那条的 `result` 换成 `URANIUM.nugget()`，配方语义从「提炼」变成「回收」：
废料里剩下的铀不够一整锭。生成物只有 `refining/nuclear_waste.json` 一处变化。
顺带把 `ModItems.NUCLEAR_WASTE` 的注释从「目前暂无用途」改成实际用途（回收铀粒 + 镎/钚尘）。

## 缸中之脑产线（接着做的一整条线）

用户给的方案很完整，只问定了四件事：营养液做成真流体 + 桶、培养缸单机单脑槽无插件、
掉落概率用推荐值（斩首者 20% / 寄生 80% / 末影人机械寄生 100%）、腐肉在原料精炼机里孵寄生虫。

### 内容

- 物品 5 个：村民大脑、末影人大脑、失活的大脑、寄生虫、机械寄生虫；营养液桶。
- 流体 `nutrient_fluid`（源 + 流动 + 类型 + 桶，无方块）；47 条「食物 → 营养液」配方由 datagen
  遍历 `DataComponents.FOOD` 生成，产量 =（饱食 + 饱和）× 100 mB。
- 两个 mob effect：`parasite`、`mechanical_parasite`（`effect/ModEffects` + `MarkedEffect`，
  `MobEffect` 构造是 protected，必须开子类）。
- 培养缸（`culture_tank`）：7 玻璃板 + 1 翡翠钢锭 + 1 无恒物质（`GGG/GJG/GEG`）。
  脑槽不消耗，按 `BrainKind` 切产出；方块右键走 `FluidUtil.interactWithFluidHandler` 支持桶进桶出。
- 配方：腐肉 → 1 寄生虫、失活大脑 → 2 寄生虫（原料精炼机）；寄生虫 + 无恒合金注入（10k~20k）→ 机械寄生虫。
- 事件 `event/ParasiteHandler`：右键感染、死亡掉脑（斩首者 20%、寄生 80%、机械寄生回收 100%）。
- 贴图脚本 `tools/textures/gen_brain_line.py`（脑 = 几个圆取并集再按深度上色，寄生虫 = 沿折线扫圆）。

### 自检（临时类跑完已删，8 项）

村民脑 205 刻：1 灵感、营养液 8000→7795、电 60000→39500、脑还在；
末影脑 405 刻：1 思维晶体、营养液 8000→4000、电耗尽；
营养液只剩 50 mB：脑变成 `inactive_brain`、进度归零；
苹果 640 mB；腐肉 → 寄生虫；失活脑 → 2 寄生虫；机械寄生村民回收 1 个寄生虫；机械寄生末影人掉 1 个末影脑。

### 三个坑

1. **`FoodProperties#saturation()` 返回的是绝对饱和度**（= 饱食 × 系数 × 2），不是修饰系数。
   第一版又乘了 2，苹果算出 2320 mB。正确写法 `(nutrition + saturation) * 100`。
2. **失活逻辑不能靠 `canIncrease` 查营养液**：查了的话进度条停住、`onTickWork` 再也不会被调用，
   脑永远不失活。村民脑的 `canIncrease` 故意放行，让 `onTickWork` 去判断并失活；末影人脑反过来
   （它不该失活，所以必须查营养液）。
3. `MobEffect` 的构造函数是 protected，注册实例得开一个空子类（`MarkedEffect`）。

## 修培养缸 GUI + 灵感值机制

### 培养缸打不开界面

原因是老坑又踩了一次：**只有 `MachineTile#onActivated` 会 `openGui()`**。培养缸为了不显示
没用的充能槽，继承的是 `PoweredTile`，于是右键什么都不发生。补一个 `onActivated` 覆写
（`openGui` + 返回 `SUCCESS`）就好了。同理以后任何直接继承 `ActiveTile` / `PoweredTile` 的方块都要自己写。

### 描述拆分与精简

- 培养缸 tooltip 只留一句总纲；两种脑的数值挪到**物品自己的 tooltip**（`client/tooltip/BrainLineTooltips`，
  按物品查语言键、按 `\n` 切行）。寄生虫 / 机械寄生虫 / 失活大脑也各加了一行。
- 顺手把所有机器 tooltip 压了一遍（RTG、结构模拟机、地核钻探者、流体提取机、原料精炼机都短了一半），
  只留「吃什么、产出什么、多久」。

### 灵感值

- 玩家 attachment `player/InspirationValue`（上限 1000，`serialize(Codec.INT)`）。
  合成 / 吃食物 / 拿到经验各 +1（`event/InspirationGainHandler`）。**原来的两条灵感合成配方删掉**。
- 提取：100 点 → 1 枚灵感，走 `ExtractInspirationPayload`；背包满了掉在脚下。
- 同步：`SyncInspirationValuePayload` 在 set/add、登录、克隆时下发；客户端缓存就放在
  `InspirationValue.synced` 这个 **common 类字段**里 —— 让 payload handler 去引客户端类会在服务端加载时炸。
- 界面：`client/gui/InspirationGauge` 是个 20×74 的自定义控件（上面 50 高进度条、下面 20 高按钮，
  按钮画灵感图标），由 `ScreenEvent.Init.Post` 挂到 `InventoryScreen` 的 `guiLeft + 180`。
