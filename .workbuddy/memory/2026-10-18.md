# 2026-10-18

## 修 Gradle 炸掉（结构模拟机引入 MBD2 引起的连锁问题）

用户反馈「gradle 炸了、运行不了、IDEA 里一堆报错」。排查后是三个问题叠加。

### 根因 1（致命）：testCompileClasspath 拉进了一个从没下载过的依赖

`testCompileClasspath` 默认继承 `implementation`，于是把 MBD2 / LDLib2 传递来的
`kotlin-stdlib 2.1.20 -> org.jetbrains:annotations:13.0` 也拉进来解析。
项目**根本没有 `src/test`**，这个解析纯属白做，而 13.0 本地没缓存（缓存里只有
NeoForge 带来的 24.1.0 / 26.1.0），于是：

- `./gradlew build --offline` → `No cached version available for offline mode`，直接失败
- 联网跑 → 卡在下载，5 分钟都不够
- IDEA 同步要解析全部 configuration → 同样卡住 → **同步失败 → 依赖没导入 → 满屏红色报错**

这解释了「IDEA 里一堆报错」：不是代码错，是同步没成功导致 import 全红。

**修法（build.gradle 两处）**：

1. `configurations.configureEach { resolutionStrategy { force 'org.jetbrains:annotations:26.1.0' } }`
   —— 26.1.0 的 jar/pom/module 在缓存里都齐全，注解类向后兼容，不再需要联网拿 13.0。
2. `tasks.named('compileTestJava') { enabled = false }` + `tasks.named('test') { enabled = false }`
   —— 没有测试源码就没必要编译测试。

**注意**：只禁用任务**不够**。配置缓存序列化时仍会去解析那个 task 的 `classpath` 字段，
报错就是 `field classpath of task :compileTestJava ... error writing value`。
必须在依赖层面解决，禁用任务只是顺带的语义清理。

### 根因 2：Gradle daemon 内存太小 → 反复被 OS 杀

`gradle.properties` 里 `-Xmx1G`。加了 MBD2 + LDLib2 两个大库（LDLib2 还是 `-all` fat jar）
之后，配置阶段 1G 不够，`~/.gradle/daemon/9.2.1/` 下堆了 **298 个日志、84MB**，
`gradlew --status` 一片 `STOPPED (by user or operating system)`，
联网跑 `build` 时直接 `Gradle build daemon disappeared unexpectedly`。

**修法**：`-Xmx1G` → `-Xmx3G`。改完后配置缓存能正常复用（`Configuration cache entry reused.`）。

### 环境事实（排查时确认的，以后有用）

- `JAVA_HOME=D:\1`，是 **Java 25.0.2**（Oracle）。Gradle daemon 跑在 25 上。
- 但**游戏本身用的是 JDK 21**：toolchain 自动下载的
  `C:\Users\zzz\.gradle\jdks\jetbrains_s_r_o_-21-amd64-windows.2`，与 `JavaLanguageVersion.of(21)` 一致。
- 系统里还有 `/c/Program Files/Java/jdk-21`（若以后 25 上跑 Gradle 出怪问题，可把
  IDEA 的 Gradle JVM 指到这里，本次没改）。

### 验证结果（全部离线）

- `build --offline` → BUILD SUCCESSFUL（第二次跑复用配置缓存，7s）
- `generateModMetadata --offline` → 成功（这条是 `neoForge.ideSyncTask` 走的，等于验了 IDEA 同步路径）
- `runData --offline` → 成功，527→528 文件
- `runServer --offline` → `Done (1.310s)! For help, type "help"`；
  日志里 `Found valid mod file ... with {mbd2} mods - versions {21.1.1}`、
  `LowDragLib2 2.2.39.a (ldlib2)`、`Multiblocked2 21.1.1 (mbd2)` → 两个库运行时都正常加载
  （`BUILD FAILED ... exit value 143` 是我用 timeout 强杀的 SIGTERM，不是真失败）

### 给用户的话

改完要在 IDEA 里 **Reload Gradle Project**（Gradle 工具窗口的刷新按钮），红色才会消。
若之后 daemon 还莫名消失，就把 IDEA 的 Gradle JVM 换成 JDK 21。
`~/.gradle/daemon/9.2.1/` 下 298 个历史日志（84MB）可以直接删，只是日志。

## 结构模拟机四项修复（用户实测反馈）

### 1. 高能机器外壳在物品栏里是黑紫块

不是贴图颜色的问题 —— 贴图本身是正常的亮紫 (212,175,230)。**黑紫棋盘格是 MC 的「缺失贴图」**，
真正缺的是 `models/item/high_energy_machine_casing.json`：`ModItemModelsProvider` 里只给两份
结构数据写了 `basicItem`，漏了外壳的 `blockItem(...)`。世界里显示正常（blockstate + block model
都在），只有物品栏是黑的 —— 这个现象是判断「缺 item model」还是「缺贴图」的关键区别。

### 2. 结构成型不了的排查（重点）

先写自检在四个朝向上各搭一次，结果**全部 formed=true**。但这里有个陷阱：
如果自检用 `SimulatorPattern.previewCells` 来摆方块，那就和预览共用同一套坐标，
**自检通过只能证明「自己和自己一致」**，证明不了预览和 MBD2 的成型判定一致。

所以自检故意**不复用** `SimulatorPattern.rotate`，而是照 MBD2 的
`setActualRelativeOffset` 手工展开成四个朝向的 switch（列沿 LEFT、层沿 FRONT、行沿 +Y）。
这样两边独立，四条全过才说明映射真的一致。核对源码也确认了：
`RelativeDirection.LEFT = Direction::getCounterClockWise`、`FRONT = Function.identity()`，
与 `previewCells` 的写法一致。

结论：**成型逻辑没问题，是玩家不知道该往哪放**（4×3×3、主方块在正面中层左二，太反直觉）。
两条改进：
- 内部两格 `Predicates.air()` → `Predicates.any()`：留空、塞满外壳、放杂物都算成型。
  实测「内部留空」与「内部塞满」都 formed=true。原来要求精确数着别填，几乎必踩。
- 加投影仪 + JEI 预览（见下）。

### 3. 结构投影仪（替代「手持主方块就出虚影」）

- `multiblock/item/ProjectorItem`，由「铁锭 + 思维矩阵锭」注入得到（1 级，50k~150k FE）。
- `client/ProjectorPreviewHandler`：客户端记 anchor / facing / 到期刻 / 所在维度，
  `PlayerInteractEvent.RightClickBlock` 里判断「手里的物品是 ProjectorItem 且点的是控制器」。
- `StructureSimulatorTile#onActivated` 覆写：主手持投影仪时返回 `ItemInteractionResult.SUCCESS`，
  **不开界面** —— 否则 GUI 一起就把虚影挡住了。
- 旧逻辑（手持控制器就跟着准星画）整段删掉，渲染器改成读 handler 的状态。

### 4. JEI 结构预览

`jei/category/StructurePreviewCategory` + `StructurePreview(int layer)`：
**每层注册成一条配方**，JEI 翻页就是翻层，不用自己写翻页交互。
`draw` 里手绘 4×3 网格（槽位之间有间隙，摆出来像零件清单而不是结构）。
注意 `draw` 在槽位之后执行，所以底部分隔线以下那个控制器小槽位必须避开手绘区域。

背景 `structure_preview.png` 用 `gen_jei_background.py` 生成，给 `shaft_x` 传负数让
`draw_arrow` 整个跳过（这个面板画的是方块网格，没有「输入→输出」的方向）。

### 5. 仓室不再画箭头

输入仓 / 输出仓共用同一枚横向槽口，**只靠颜色区分**（绿=进、橙=出）。
`gen_simulator_textures.py` 里的 `arrow_down/arrow_up` 合并成 `slot()`。

### 验证

`build` / `runData`（530→531 文件）/ `runServer` 全过；成型自检两种搭法都 formed=true；
`jar` 已重跑，169 张贴图、投影仪模型与配方都在，无自检类残留。
**客户端目视仍未做**：投影仪虚影的实际观感、JEI 结构预览的对齐、外壳物品栏图标，需要 `runClient`。

## 「卡在 Calculating task graph / configuration cache cannot be reused」的定位

用户反馈：输出只有 `Starting Gradle Daemon` + `Gradle Daemon started` +
`Calculating task graph as configuration cache cannot be reused because file
'gradle.properties' has changed.` 就不再动了。

**那行不是错误**，是 INFO：配置缓存的 key 含 gradle.properties 的内容/时间戳，改过就失效，
需要重新算一次任务图（实测 11s，第二次命中缓存 7s）。真正的坑是**死循环**：
配置阶段被中断 → 缓存条目**不会被写入** → 下次比对还是「gradle.properties 变过」→
于是每次都打印同一句、每次都从头配置，看起来就像永远卡在那行。

证据在 `~/.gradle/daemon/9.2.1/daemon-*.out.log`（今天已堆到 319 个）：
- `daemon-49072`：打印完那行就是 `Daemon will be stopped at the end of the build
  stop command received` → 有人（或 IDEA）在构建途中下了 `--stop`。
- `daemon-36920`：打印完那行就是 `Daemon vm is shutting down ... user interrupt`。

**中断的两个来源**：① 构建跑到一半执行 `./gradlew --stop`（会连正在跑的构建一起杀）；
② 客户端被取消/超时。另有两个放大因素：
- **两套 JVM**：命令行 daemon 走 `JAVA_HOME=D:\1`（Java 25），IDEA 走自己设的 jdk-21，
  于是两个 daemon 池、各算各的配置缓存、内存翻倍。
  → 已在 `gradle.properties` 加 `org.gradle.java.home=C:\\Program Files\\Java\\jdk-21` 统一。
- **内存吃紧**：整机 31.5G 只剩 1.9G 空闲，其中有个常驻的
  `lwjgl3ify-forgePatches.jar nogui -Xms8G -Xmx8G`（用户自己的 MC 服务端，占 6.4G）。
  `-Xms8G` 会立即预提交 8G，是主要压力源。跑 Gradle 时最好先停它或把 -Xmx 调小。

排查手法：卡住时去看最新那个 `daemon-*.out.log` 的**最后几行**，以及任务管理器里的
java 进程；命令行加 `--console=plain`（有进度条）或 `--info`。
